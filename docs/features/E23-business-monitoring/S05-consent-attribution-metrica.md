#### Граница подсчёта и хранения

- Caddy отмечает только запросы к `astrotype.ru` (не `www`), к точному `GET /` без query; входящий маркер перезаписывается для разрешённого маршрута и удаляется на остальных маршрутах к Next.js. Next.js требует навигацию верхнего уровня с `Sec-Fetch-Mode: navigate`, `Sec-Fetch-Dest: document` и `Accept: text/html`. Prefetch/prerender, RSC и Next-router запросы, `Authorization` и draft-preview не учитываются. Обновление страницы считается повторно, если запрос снова удовлетворяет критериям. Боты могут имитировать навигацию.
- Наблюдение — завершение `200 text/html` на сервере Next.js, а не факт получения, просмотра или чтения документа человеком. `304`, ошибки, открытия только из кеша браузера/CDN, bfcache и клиентские переходы без подходящего запроса не попадают в счётчик. Ограничение нагрузки, сбои и перезапуск могут пропустить даже подходящий запрос. Неполное покрытие допускается осознанно: число — только записанные наблюдения, `null` — нет данных, подтверждённый ноль не публикуется.
- Next.js после ответа отправляет пустой сигнал без пользовательских данных, максимум четыре одновременных отправки на процесс, без повторов. Приёмник `POST /_internal/landing-document` доступен только по приватной сети сервисов production Compose; на публичном Caddy маршруте возвращается `404`. Маркер сигнала не заменяет изоляцию сети. Обработчик минует middleware журнала/лимитов, а точный внутренний путь исключён из access log Uvicorn; обычные журналы приложения не используются для подсчёта.
- Redis хранит только `business:landing-documents:v1:YYYY-MM-DD` и целое число; день — дата получения сигнала бекендом в `Europe/Moscow`. `INCR` и абсолютный `EXPIREAT` выполняются атомарно, срок — 30 дней от начала дня, не продлевается повторными записями. API отдаёт `landing_documents` с `through_date` и `observed` за 30 московских дат, включая текущую неполную дату, независимо от выбранного периода других показателей. При выключении или отказе чтения значение недоступно.
- Только API подключается по `LANDING_DOCUMENT_REDIS_URL` к отдельному `landing-redis` в сети `landing-storage` (`internal: true`); порт не опубликован. Общий Redis для приложения и Celery сохраняет прежний AOF и том и не используется как запасное хранилище. При отсутствии или отказе отдельного Redis приёмник возвращает `503`, обзор — `observed: null`, а главная остаётся доступна.
- Приёмник передаёт Redis абсолютный дедлайн на 250 мс от приёма сигнала. Lua проверяет `TIME` по общим для контейнеров часам хоста до `INCR` и не меняет ключ или его TTL на дедлайне либо позже, в том числе при восстановлении связи. Дедлайн не хранится; `503` не повторяется и сам по себе не доказывает отсутствие записи, если Redis успел выполнить её, но ответ потерялся.
- У `landing-redis` выключены AOF и автоматические RDB-снимки; Redis ACL запрещает ручные снимки, смену настроек и репликацию. Корень контейнера доступен только для чтения, `/data` — `tmpfs` вместо встроенного тома образа, swap контейнера отключён. Не копировать память процесса/ВМ и `tmpfs` в backup. Перезапуск Redis безвозвратно теряет **все** наблюдения, включая ещё не истёкшие; после перезапуска `observed: null`, пока не получен новый сигнал. Следующее ненулевое значение содержит только сохранившиеся наблюдения, а не восстановленный трафик за 30 дней.
- `LANDING_DOCUMENT_COUNTER_ENABLED` по умолчанию `false` для Caddy, Next.js и API. Отключение флага прекращает новый сбор и скрывает показатель; не меняет главную и не требует трогать DNS, авторизацию или оплаты.

#### Приёмка в production

1. Выкатить кандидат с выключенным флагом, используя отдельный overlay, который сохраняет действующий recovery ingress; не заменять активный ingress базовым Caddyfile; при выборочной выкладке с `--no-deps` поднять `landing-redis` явно. Сверить действующие настройки Redis (`appendonly=no`, пустой `save`, `+time` в ACL отдельного Redis), отсутствие постоянного тома/порта, приватную сеть только API и Redis, запрет swap и исключение эфемерного хранилища из backup. Сверить, что общий Redis не изменился. Проверить, что до выкладки старый счётчик не писал в общий Redis: если писал, отдельно разбирать ключи и старые копии; новое хранилище их не очищает и не импортирует.
2. Подтвердить `404` на публичном приёмнике, отсутствие прироста при выключенном флаге и обычный `200` на главной. Включить один и тот же флаг для Caddy, Next.js и API, затем сверить прирост от подходящей навигации и отсутствие прироста от исключённых запросов; проверить отсутствие сигнала в access logs.
3. Сверить защищённый API (`401` без сессии, `403` обычному аккаунту, `200` и `Cache-Control: no-store` админу), дневное значение Redis и отражённый агрегат в `/admin/business`. При отказе любого условия выключить флаг во всех трёх сервисах; не переключать счётчик на общий Redis.

## Implemented boundary

- No vendor loader or `ym` adapter ships on the app origin. Code loaded on a clean landing could still read persisted `astrotype-auth` data and report IDs in session storage. Neither opt-in nor full-document navigation isolates that storage. Only the first-party consent/handoff and an always-reachable revocation control are mounted. First-party capture rejects dirty current **or original** navigation URLs and unsafe referrers. Registration/login keep full-document links, without interception or delay. Next and the Caddy edge apply `Referrer-Policy: no-referrer`; the edge replaces upstream values rather than adding a duplicate. No automatic goal or payment instrumentation was added.
- `POST /api/v1/analytics/events` admits only `report_opened`, with canonical artifact UUID, `self` / `career` / `child`, and no extra fields. The collector uses the authenticated account plus each product's metadata-only ownership check and access decision; it does not read report content or reconcile payments. Missing, foreign and locked targets get the same answer. One first-party observation per owner and artifact is persisted in the existing internal event/outbox transaction, not inferred from report GETs. Activation of reader call sites is separate; this slice delivers and exercises the collector interface.
- All writes require an exact configured `Origin`, same-origin Fetch Metadata when present, `X-Analytics-Request: 1`, and bounded JSON (1 KiB, no extra/duplicate fields). Per-owner or anonymous IP Redis limits are atomic and fail closed. Errors never echo request values. Collector admission uses existing `BUSINESS_MONITORING_ENABLED` (default false).
- Attribution capture is consented on the clean landing only. The app sends a null ClientID and asserts the **server-approved** policy version. For any known ClientID, `source_counter_id` must be the canonical decimal string of the counter used to read it and must match the one server-approved counter; it is a source assertion, not a destination selector. The server timestamps the capture and pins its configured counter and policy in an opaque, single-use Redis receipt (30-minute TTL). Attach rejects receipts from a different policy/counter or legacy receipts lacking counter provenance. Only the receipt is passed to the auth/session write, which derives the owner from authentication. An expired/rejected receipt cannot permanently suppress a later capture; a known observation in the mock harness can supersede a pending null receipt, and a later null observation cannot erase or refresh a known owner binding. A missing observation cannot delay the product flow. A future bounded ClientID would be a browser observation, not independent proof of vendor identity.
- Browser revocation stops first-party capture and discards the pending handoff. The landing always offers authenticated account revocation, even with no local consent record and policy/collection disabled. If the account write cannot be confirmed, it asks the user to sign in and retry. The committed revoke clears the ClientID and counter and leaves a short-lived tombstone so a receipt captured before revocation cannot restore the old consent. Expiry blocks eligibility; `purge_expired_attribution` is an unscheduled storage primitive, not activation of a destructive job.
- Backend policy admission is independently default-off: process env `ANALYTICS_ATTRIBUTION_POLICY_APPROVED=true`, `ANALYTICS_ATTRIBUTION_POLICY_VERSION`, `ANALYTICS_ATTRIBUTION_RETENTION_DAYS` (`1..90`), and a canonical positive `ANALYTICS_ATTRIBUTION_COUNTER_ID` (PostgreSQL bigint range) are all required. No deployment configuration or actual policy values were activated.

## S08 read interface

`app.modules.analytics.attribution.read_active_attribution(session, *, owner_id, approved_policy_version, approved_counter_id, occurred_at, now, for_dispatch=False) -> ActiveAttribution | None`. Pass the canonical event owner and aware original event time, the current aware clock, and the export destination's policy version and counter. Only a known, unexpired ClientID bound before the event and matching both the currently approved and stored counter is eligible. `e23s08b001` follows `e23s07t001`, adds a nullable counter without a default or backfill, and leaves legacy null-bound rows ineligible until a fresh, valid capture is bound. Changing the deployment setting never relabels an old receipt or ClientID.

Initial admission is a read-only preflight. Final S08 admission uses `for_dispatch=True` and holds the eligible owner's row lock through the bounded HTTP attempt. S05's revoke upsert must obtain that same row lock: a revoke committed first prevents dispatch; a dispatch admitted first may complete or time out before revoke commits. A revoke does not recall bytes already sent. See [S08](./S08-yandex-conversion-export.md) for the failure and no-replay rules.
