# Astrotype — Dashboard UX/UI: рекомендации

**Объект:** главный экран личного кабинета Astrotype  
**Основание:** скриншот кабинета от 14.10.2026  
**Статус:** продуктовые рекомендации к бэклогу, не результаты пользовательского тестирования

## 1. Краткий вывод

Кабинет уже выглядит как единый premium SaaS-продукт: последовательный тёмный интерфейс, понятная боковая навигация, быстрый доступ к последнему отчёту, отображение Plus и витрина специализированных направлений.

**Главная зона роста — не редизайн, а продуктовая ясность:** пользователю должно быть сразу понятно, что уже создано, что доступно сейчас, что появится позже и какое действие имеет смысл выполнить следующим.

## 2. Что сохранить

- **Визуальный язык:** тёмная тема, умеренные акценты, минимализм и единый стиль карточек.
- **Быстрый вход в последний отчёт:** полезен для повторных посещений.
- **Отдельный статус Plus:** подписка и дата окончания доступны без поиска по настройкам.
- **Архитектуру «один профиль → несколько отчётов»:** Self, Career, Child, Love как направления одной платформы.
- **Сайдбар:** базовая структура навигации уже подходит для MVP.

## 4. Рекомендуемая модель состояний

Состояния **доступности продукта** и **наличия отчёта** следует хранить отдельно.

| Измерение            | Возможные значения                                        |
| -------------------- | --------------------------------------------------------- |
| `product_status`     | `available`, `coming_soon`, `disabled`                    |
| `entitlement_status` | `included`, `upgrade_required`, `not_applicable`          |
| `report_status`      | `not_created`, `in_progress`, `ready`, `update_available` |

**Правило отображения:**

- **Доступно сейчас** — модуль работает, пользователь может перейти к сценарию.
- **Открыто в Plus** — модуль работает и включён в подписку.
- **Скоро · будет включено в Plus** — модуль ещё не запущен, но будет доступен по действующему тарифу согласно условиям продукта.
- **Требуется Plus** — модуль работает, но доступ отсутствует.

Не показывать «Открыто» как главный статус у ещё не выпущенного модуля.

> На скриншоте **Career отображается доступным в Plus**, а **Child и Love — будущими**. Не нужно визуально переводить Career в состояние «скоро».

## 5. Логика главного действия (Next Best Action)

Главный CTA выбирается по данным пользователя, а не задаётся статически:

```text
Если отчёта нет                 → Создать личный отчёт
Если отчёт создаётся            → Продолжить оформление
Если готовый отчёт не просмотрен→ Открыть личный отчёт
Если есть Child Age Update      → Посмотреть возрастное обновление
Если всё актуально              → Продолжить чтение / Открыть Career
```

**Важно:** при нескольких возможных действиях показывать одно основное и максимум одно дополнительное. Для пользователя с активным Plus не ставить «Оплату и доступ» рядом с главным CTA на равных основаниях.

## 6. Предлагаемые тексты карточек

### Self — Личный отчёт

> Ваш натальный портрет: основные темы, привычные реакции, сильные стороны и точки для саморефлексии.

**CTA:** `Открыть отчёт` / `Создать отчёт` (по состоянию).

### Career — Карьера

> Какой стиль работы вам ближе, что мотивирует и какие профессиональные роли стоит исследовать.

**CTA:** `Открыть Career` (если доступно) / `Узнать подробнее`.

### Child — Ребёнок

> Подсказки родителю по общению, поддержке и границам с учётом возраста ребёнка. Основа — взаимодействие родителя и ребёнка, а не ярлыки о характере ребёнка.

**Статус:** `Скоро`; при необходимости — отдельно `Будет включено в Plus`.

### Love — Отношения

> Исследуйте привычные сценарии общения, ожидания и возможные точки взаимопонимания в паре.

**Статус:** `Скоро`.

## 7. Рекомендуемая структура dashboard v2

```text
[Сайдбар: Главная / Self / Career / Child / Love]

[Hero]
  Приветствие + короткий контекст
  1 главный CTA (Next Best Action)
  Краткая информация о последнем отчёте

[Мои отчёты]
  Только существующие отчёты и их актуальные состояния

[Что можно открыть]
  Карточки доступных и будущих направлений
  Польза + реальный статус + релевантное действие

[Мой доступ]
  Plus / дата окончания / управление подпиской

[Актуально для вас] — в будущем
  Возрастные обновления Child, другие содержательные изменения
```

**Примечание:** блок подписки можно оставить выше, если именно так он лучше решает текущие задачи пользователей. Предложенный порядок — гипотеза для проверки, не обязательный редизайн.

## 8. Условия масштабирования

При запуске Child Report понадобится поддержка нескольких детей и возрастных версий:

```text
Аккаунт пользователя
├── Self Report
├── Career Report
├── Child: ребёнок A
│   ├── Core Relationship Report
│   └── Current Age Guidance (обновляемый)
└── Child: ребёнок B
    ├── Core Relationship Report
    └── Current Age Guidance (обновляемый)
```

Dashboard должен показывать `update_available` для конкретного ребёнка, **не смешивая обновление возрастного блока с созданием нового полного отчёта**.

## 9. Критерии готовности

- [ ] По каждой карточке понятно, **работает ли модуль сейчас**, **входит ли в подписку** и **есть ли созданный отчёт**.
- [ ] У hero ровно одно доминирующее действие, соответствующее состоянию аккаунта.
- [ ] Карточки продуктов описывают пользу, а не только тему.
- [ ] Существующие отчёты визуально отделены от ещё не созданных и будущих модулей.
- [ ] Пользователь с активным Plus не видит оплату как приоритетное действие без причины.
- [ ] Интерфейс допускает несколько Child Reports и отметку о возрастном обновлении.
- [ ] На мобильной ширине навигация, статусы и основные действия остаются понятными (требует отдельной проверки).

## 10. Как проверить результат

Минимальный набор продуктовых метрик:

- `dashboard → report_open` — открытие уже созданного отчёта;
- `dashboard → feature_start` — переход к созданию нового направления;
- доля пользователей, понимающих разницу между «Скоро» и «Открыто в Plus» в коротком UX-тесте;
- `update_available → update_opened` — использование возрастных обновлений Child после релиза;
- возвраты в кабинет за 7/30 дней.

**Рекомендуемая последовательность:** сначала P0 (ясность статусов и главный CTA), затем P1 (содержание карточек и организация отчётов), после этого P2 (оптимизация и возвратность). **Полный визуальный редизайн не требуется.**
