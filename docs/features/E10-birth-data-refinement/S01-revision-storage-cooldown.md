# S01: Хранилище ревизий и атомарный cooldown

## Статус

⬜ Не начато

## Контекст

Обычное изменение строки `person_profiles` не позволяет доказать, что именно поменялось, сохранить старые исходные данные или надёжно ограничить частоту. Cooldown нельзя строить только на Redis/клиенте: ключ может исчезнуть, а параллельные запросы обойдут проверку.

## Что сделать

1. Добавить additive-миграцией таблицу `profile_birth_data_revisions`.
2. Хранить `user_id`, `profile_id`, предыдущий и новый снимки, `changed_fields`, статус пересчёта, `generation_id`, итоговые `chart_id`/`report_id`, `created_at` и ошибки без секретов.
3. Использовать строку последней успешной ревизии как durable source of truth для 24-часового окна.
4. Сериализовать создание ревизии на уровне аккаунта: row/advisory lock + проверка последней ревизии внутри одной транзакции.
5. Зафиксировать профиль, ревизию, generation/outbox-запись атомарно; отправлять фоновую задачу после commit с гарантированным retry.
6. Добавить индексы `(user_id, created_at desc)` и `(profile_id, created_at desc)`.
7. Не удалять и не изменять исторические ревизии при последующих обновлениях.

## Предлагаемая модель

| Поле                | Назначение                                                        |
| ------------------- | ----------------------------------------------------------------- |
| `id`                | UUID ревизии                                                      |
| `user_id`           | Владелец и область cooldown                                       |
| `profile_id`        | Изменённый профиль                                                |
| `previous_snapshot` | Время/точность/place/lat/lon/timezone до изменения                |
| `new_snapshot`      | Полный итоговый снимок                                            |
| `changed_fields`    | Стабильный список изменённых доменных полей                       |
| `status`            | `queued`, `processing`, `deterministic_ready`, `ready`, `failed`  |
| `generation_id`     | Идентификатор фонового пересчёта                                  |
| `chart_id`          | Новая версия карты после расчёта                                  |
| `report_id`         | Новая версия отчёта после расчёта                                 |
| `error_code`        | Безопасный машинный код ошибки, без персональных данных/traceback |
| `created_at`        | Момент успешной фиксации и начало cooldown                        |

## Инварианты

```text
cooldown_scope = user_id
cooldown_window = [last_success.created_at, last_success.created_at + 24h)
server_clock = UTC
```

- Только committed-ревизия расходует лимит.
- Запрос ровно в `next_available_at` разрешён.
- Все profile ID одного аккаунта входят в одно окно.
- Идемпотентный replay возвращает исходный результат и не создаёт новую ревизию.
- Redis допустим только как ускоряющий cache, но не source of truth.

## Критерии приёмки

- [ ] Миграция не удаляет и не переписывает существующие профили, карты и отчёты.
- [ ] Успешная ревизия сохраняет снимки до/после и `changed_fields`.
- [ ] Второй успешный запрос до истечения 24 часов невозможен для любого профиля аккаунта.
- [ ] Два конкурентных запроса дают ровно одну committed-ревизию.
- [ ] Неуспешный/no-op запрос не расходует лимит.
- [ ] Граница `next_available_at` покрыта тестом с управляемыми часами.
- [ ] Исторические ревизии неизменяемы и доступны только владельцу/внутреннему сервису.
- [ ] Персональные данные снимков не попадают в application logs и метрики.
