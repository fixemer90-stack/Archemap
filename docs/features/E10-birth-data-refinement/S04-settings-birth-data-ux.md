# S04: UX и визуальный дизайн данных рождения в Settings

## Статус

⬜ Не начато

## Контекст

Сейчас `/settings` содержит имя, email и смену пароля в узкой последовательности базовых glass-карточек. Пользователь не видит полные исходные данные расчёта и не может безопасно инициировать их уточнение. Добавление сложного stateful-сценария в текущую композицию без отдельного дизайн-контракта превратит страницу в длинную форму без ясной иерархии.

## Условие дизайн-задачи

Редизайн `/settings` выполняется в рамках E10 и должен в первую очередь поддержать безопасное уточнение данных рождения. Это не отдельный маркетинговый редизайн и не разрешение переносить landing-page приёмы в служебный интерфейс без адаптации.

Визуальное направление берётся из:

- [дизайн-ревью главной страницы Astrotype v2](../../design/astrotype-v2-homepage-sample-review.md);
- [образца главной страницы Astrotype v2](../../design/astrotype-v2-homepage-sample.html).

Обязательные условия применения направления:

- сохранить тёмную молочно-золотую систему, редакционную типографику и ощущение единого продукта;
- не копировать крупный landing hero, маркетинговые proof-блоки и декоративную перегруженность;
- не создавать «card soup» из нескольких уровней одинаковых glass-поверхностей;
- сначала обеспечить понятность формы, состояния операции, доступность и mobile layout;
- выполнить относящиеся к общему UI требования review: отсутствие горизонтального переполнения, читаемый базовый текст, `focus-visible`, touch-target не менее `44 × 44px`, reduced-motion и проверка на ширинах от `320px`.

## Что сделать

Добавить основной блок «Данные рождения» и перестроить порядок страницы так, чтобы сценарий E10 располагался перед вторичными настройками профиля и безопасности.

Одновременно привести `/settings` к цельной продуктовой композиции, в которой данные рождения являются главным функциональным блоком E10, а имя, email и пароль остаются доступными независимыми настройками.

## Дизайн-контракт страницы

### Информационная иерархия

Порядок блоков:

1. Заголовок «Настройки» и короткое пользовательское пояснение без технических терминов.
2. Основной блок «Данные рождения» с текущим состоянием, профилем, cooldown и действием уточнения.
3. Блок «Профиль» с именем и неизменяемым email.
4. Блок «Безопасность» со сменой пароля.

На desktop блок данных рождения может занимать всю основную ширину страницы, а «Профиль» и «Безопасность» располагаться ниже в двухколоночной сетке при достаточной ширине. На mobile все блоки переходят в одну колонку без горизонтального скролла.

### Визуальная композиция

- Использовать спокойный тёмный фон и поверхности, согласованные с отчётом и направлением главной страницы.
- Использовать молочный основной текст, приглушённый вторичный текст и золото только для иерархии и главного действия.
- Редакционную антикву применять к заголовку страницы и заголовкам крупных блоков; поля, пояснения, статусы и кнопки должны использовать читаемый интерфейсный гротеск.
- Базовый пользовательский текст — не менее `16px`; служебные подписи не уменьшать до плохо читаемого декоративного текста.
- Не вкладывать каждое поле в отдельную glass-карточку. Текущие значения собрать в компактный semantic summary или definition list.
- На экране не должно быть одновременно нескольких конкурирующих золотых CTA. Главным действием является «Уточнить данные» или «Сохранить изменения» в зависимости от состояния.
- Имя, email и пароль визуально остаются вторичными по отношению к сценарию E10, но не выглядят отключёнными или устаревшими.

### Состояние просмотра

Показывать:

- выбранный профиль; при нескольких профилях — явный selector;
- время рождения или «Время не указано»;
- понятную точность: «Точное», «Примерное», «Неизвестно»;
- место рождения;
- спокойное пояснение: «Изменение времени или места повлияет на натальную карту и отчёт»;
- кнопку «Уточнить данные»;
- серверное `next_available_at`, если действует ограничение.

Композиция состояния просмотра:

- в верхней части блока — название, короткое объяснение и status badge;
- при нескольких профилях selector находится до значений и явно сообщает, чьи данные показаны;
- время, точность и место выводятся как три понятные строки со значением и пояснением, а не как disabled-поля формы;
- действие «Уточнить данные» находится рядом с объяснением последствий, но не выглядит опасным;
- дата рождения может отображаться как неизменяемый контекст, но не получает affordance редактирования.

### Состояние редактирования

- Поле времени `HH:MM`.
- Выбор точности `exact / approximate / unknown` с человеческими подписями.
- Поиск места с debounce и выбором конкретной подсказки.
- Координаты/timezone скрыты от ручного редактирования.
- Кнопка сохранения активна только при валидной выбранной подсказке и материальном изменении.
- Перед отправкой — подтверждение: будет создан новый расчёт, текущий отчёт останется доступен до готовности.

Редактирование раскрывается внутри основного блока или в отдельной полноширинной панели того же контекста. Не использовать узкий modal для геокодера и нескольких взаимозависимых полей.

Форма должна:

- визуально разделять «Время рождения» и «Место рождения»;
- объяснять влияние `exact / approximate / unknown` непосредственно возле выбора точности;
- показывать выбранную подсказку места как подтверждённое значение;
- иметь вторичное действие «Отменить» и одно основное «Проверить изменения»;
- перед финальной отправкой показывать компактное сравнение «Было / Стало» только для изменённых полей;
- не выводить пользователю latitude, longitude, IANA timezone, input hash или generation ID.

### Состояние cooldown

Кнопка выключена, но данные доступны для просмотра. Текст строится по серверному timestamp, например:

```text
Следующее уточнение будет доступно 14 сентября в 13:00.
```

Не использовать только локальный 24-часовой таймер как источник истины. После фокуса окна/возврата на страницу статус перечитывается с backend.

Cooldown оформляется как спокойное информационное состояние, а не как ошибка:

- не окрашивать весь блок красным;
- сохранить читаемыми текущие данные;
- показать абсолютную дату и время следующей доступности;
- при необходимости добавить относительное пояснение, но не использовать клиентский countdown как источник истины;
- отключённая кнопка должна сохранять читаемую подпись и объяснение причины через видимый текст, а не только tooltip.

### Состояние пересчёта

После `202`:

- показать «Данные сохранены — обновляем расчёт»;
- отслеживать revision/generation status;
- сохранить доступ к текущему отчёту;
- при `deterministic_ready` предложить открыть обновлённый отчёт;
- при `failed` не обещать потерянный результат и не предлагать оплатить снова.

Визуальный state machine:

| Состояние | Пользовательский заголовок | Основное действие |
|---|---|---|
| `queued` | «Данные сохранены» | «Открыть текущий отчёт» |
| `processing` | «Обновляем натальную карту» | «Открыть текущий отчёт» |
| `deterministic_ready` | «Обновлённый отчёт уже доступен» | «Открыть обновлённый отчёт» |
| `ready` | «Отчёт обновлён» | «Открыть отчёт» |
| `failed` | «Не удалось завершить обновление» | «Открыть сохранённый отчёт» |

Не использовать skeleton, который скрывает прежний результат. Прогресс должен быть компактным, не блокировать остальные настройки и не создавать ложный процент выполнения, если backend его не предоставляет.

### Ошибки

- `429`: обновить UI по `next_available_at`, не показывать общий сбой.
- `birth_data_unchanged`: объяснить, что данные не отличаются.
- Геокодер недоступен: не разрешать сохранить произвольные координаты/default timezone.
- Session expired: стандартный auth-refresh/login flow.

Ошибки показываются возле связанного поля или внутри блока операции. Общий destructive banner используется только для ошибки, влияющей на весь сценарий. Цвет не должен быть единственным носителем смысла.

## Responsive-контракт

Контрольные ширины: `320`, `360`, `390`, `430`, `768`, `1024`, `1440px`.

- На ширинах до `767px` используется одна колонка.
- Поля времени и точности не сжимаются до нечитаемого состояния; при необходимости располагаются друг под другом.
- Геокодер и список подсказок не выходят за viewport и не перекрываются экранной клавиатурой без возможности прокрутки.
- Основные действия на mobile занимают доступную ширину, но их текст не обрезается.
- Значения места могут переноситься на несколько строк.
- Ни один selector, status badge, alert или button не создаёт горизонтальный scrollbar.
- Sticky-CTA не обязателен; если он используется, он не перекрывает поля, подсказки и системную клавиатуру.

## Интерактивность и motion

- Использовать короткие переходы opacity/transform для раскрытия формы и смены статусов.
- Не использовать preloader, custom cursor, параллакс или scroll-hijacking на странице настроек.
- Не задерживать отображение серверного состояния ради анимации.
- При `prefers-reduced-motion: reduce` раскрытие и смена состояний происходят без декоративного движения.
- После перехода между состояниями фокус программно перемещается только когда это помогает продолжить сценарий и не дезориентирует пользователя.

## Микрокопирайтинг

Не использовать технические слова `input_hash`, `generation_id`, `LLM`, `v2`, `timezone`. Разрешены понятные формулировки: «исходные данные», «натальная карта», «обновляем расчёт», «текущий отчёт остаётся доступен».

Также не использовать внутренние дизайн-комментарии, названия API-состояний и обещания будущих функций. Текст должен объяснять текущее действие, последствия изменения и сохранность предыдущего отчёта.

## Критерии приёмки

- [ ] Карточка корректно показывает время, точность и место выбранного профиля.
- [ ] Страница имеет ясную иерархию: данные рождения → профиль → безопасность.
- [ ] Визуальный язык согласован с направлением Astrotype v2, но utility-страница не имитирует marketing landing.
- [ ] При нескольких профилях пользователь явно выбирает изменяемый профиль.
- [ ] Нельзя изменить дату рождения в этом интерфейсе.
- [ ] Нельзя сохранить место без выбора подсказки.
- [ ] Exact/approximate/unknown корректно управляют обязательностью времени.
- [ ] Перед сохранением показано понятное сравнение изменённых значений «Было / Стало».
- [ ] UI показывает backend-derived cooldown и обновляет его после 429/refocus.
- [ ] Успех запускает понятное состояние пересчёта без скрытия старого отчёта.
- [ ] Ошибка фоновой генерации не предлагает повторную оплату.
- [ ] На ширинах `320–1440px` отсутствуют обрезание контента и горизонтальный scrollbar.
- [ ] Mobile layout, keyboard navigation, labels, error association и `focus-visible` проверены.
- [ ] Touch-target основных действий не меньше `44 × 44px`.
- [ ] Контраст, базовый размер текста и muted-подписи проверены на читаемость.
- [ ] Reduced-motion режим не теряет состояния и пользовательские действия.
- [ ] Визуально проверены view, edit, cooldown, processing, ready и failed состояния.
- [ ] Имя и смена пароля продолжают работать независимо от cooldown.

## Проверка

Минимальный набор доказательств после реализации:

1. Component tests для всех состояний birth-data блока.
2. Keyboard-only проход: selector → edit → geocoder → confirmation → submit.
3. Проверка accessible name/description и связи ошибок с полями.
4. Screenshots минимум для desktop `1440px`, tablet `768px` и mobile `390px`.
5. Отдельный smoke на `320px` для отсутствия горизонтального переполнения.
6. Проверка `prefers-reduced-motion: reduce`.
7. Реальный E10 smoke: старый отчёт остаётся доступен во время `queued/processing`.
